# CodeLens AI

AI-assisted analysis foundation for the educational Mini Python and Mini C language subsets.

## Phase 4 status

Phase 4 provides a unified multi-language analysis workspace for the Mini Python and Mini C analyzers. It adds line-numbered source input, diagnostic-to-source navigation, consistent diagnostic summaries, resilient AST visualization, and clear partial/error-node presentation. Phase 6 adds Groq-powered alternative code generation; generated code is not automatically validated or executed.

Phase 5 adds Automata Lab: an educational DFA registry and interactive simulator for identifier, integer, arithmetic-operator, relational-operator, and whitespace patterns. Phase 5.2 connects eligible analyzer tokens to the corresponding DFA.

## Architecture

- `frontend/`: React + TypeScript + Vite application.
- `backend/`: Python + FastAPI + Pydantic API.
- Frontend and backend are deployed separately.
- The frontend receives the backend URL from `VITE_API_BASE_URL`.
- No submitted source code is executed.
- Diagnostics can be selected to focus the corresponding source line and column.
- AST branches are keyboard-accessible and incomplete/error nodes are marked explicitly.

## Requirements

- Node.js 20 or newer
- Python 3.11 or newer

```powershell

.\.venv\Scripts\Activate.ps1

pip install -r requirements.txt
uvicorn app.main:app --reload
```

The backend runs at `http://127.0.0.1:8000`.

```powershell

```

The frontend runs at the URL printed by Vite, usually `http://localhost:5173`.

## Environment variables

Frontend runtime configuration:

```text
VITE_API_BASE_URL=http://127.0.0.1:8000
```

Backend runtime configuration:

```text
CODELENS_ALLOWED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

The frontend only needs `VITE_API_BASE_URL`. Configure backend values directly in the backend process or Render service environment; this repository intentionally does not create or commit environment files. Never put API keys or credentials in frontend variables.

Phase 6 backend variables:

| Variable | Required value or purpose |
| --- | --- |
| `CODELENS_AI_PROVIDER` | `groq` |
| `GROQ_API_KEY` | Secret API key from the [official Groq console](https://console.groq.com/keys) |
| `GROQ_API_BASE_URL` | Usually `https://api.groq.com/openai/v1` |
| `GROQ_MODEL` | Defaults to `openai/gpt-oss-20b`; override only with a model available to your Groq account |
| `CODELENS_AI_TIMEOUT_SECONDS` | Positive request timeout in seconds; defaults to `60` |

For Render, enter these variables under **Render Dashboard → My Backend Service → Environment**. The key stays exclusively on Render and is never sent to Vercel. Groq generation uses the official [Groq Chat Completions API](https://console.groq.com/docs/api-reference), bearer authentication, and the documented `openai/gpt-oss-20b` model. Generation can fail because of missing credentials, invalid credentials, quota, rate limits, provider outages, connectivity, or timeout. Generated code may contain syntax errors or change behavior; it is labeled **Generated by Groq — Not yet validated** and Phase 7 validation is intentionally not implemented.

## API

### `GET /api/health`

Returns a deployment-safe service status.

### `GET /api/languages`

Returns the planned Mini Python and Mini C language subsets.

### `POST /api/analyze`

Analyzes Mini Python source without executing it.

Request:

```json
{"language":"mini_python","code":"x = 10\nprint(x)\n"}
```

The response includes `lexical_valid`, `syntax_valid`, `success`, token locations, structured diagnostics, a compatibility AST in `tree`, a parser-backed hierarchical `parse_tree` with terminal lexemes and source locations, grammar version, and summary counts.

The workspace separates lexical and syntax diagnostics by stable diagnostic-code families, shows counts and severity, and provides an empty state when a category has no diagnostics. Selecting a diagnostic focuses the corresponding line and column in the source textarea. The lightweight editor uses reliable line highlighting; precise token-range background highlighting is not provided by the native textarea. Validation wording refers only to static lexical and syntax checks and does not imply execution, semantic equivalence, or runtime correctness.

The comparison report preserves raw editor text, including indentation, trailing spaces, blank lines, tabs, and newline style. Its visible diff uses `·` for edge spaces, `⇥` for tabs, and explicit LF/CRLF/CR labels. AST differences are structural only and do not establish behavioral differences.

### `POST /api/generate-alternative`

Requests a separate alternative implementation from Groq without executing either source.

Request:

```json
{"language":"mini_python","source_code":"x = 10\nprint(x)"}
```

Response:

```json
{"language":"mini_python","generated_code":"y = 10\nprint(y)","provider":"groq","model":"openai/gpt-oss-20b"}
```

Only `mini_python` and `mini_c` are accepted. Source must be non-blank and no larger than 100,000 characters. The generated response populates the separate Groq-Generated Code editor automatically; the original editor and its analysis remain unchanged. Both editors have independent deterministic validation results. The endpoint does not claim equivalence, validation, security, or execution of the generated code.

### Safe execution status

Each editor has an independent Run button and output console. Run first re-analyzes only that editor's current source; lexical or syntax diagnostics produce an `Error` status and prevent execution from starting. Valid source reaches `POST /api/execute`, whose current safe response is `Unsupported`: this repository does not include an isolated Mini Python/Mini C runtime or sandbox, so no submitted or generated code is executed. The consoles keep Editor A and Editor B output, errors, diagnostics, status, and duration separate. Output comparison appears only after two genuine successful executions and is limited to that tested run.

Do not add `exec`, `eval`, shell execution, or direct subprocess execution to the FastAPI process. A future runtime must be a separately isolated service with CPU, memory, wall-clock, output-size, filesystem, network, environment, and process-creation restrictions before the UI can report execution success.

## Automata Lab

Automata Lab demonstrates the compiler pipeline:

```text
Source Code → Lexical Analysis → Tokens → Syntax Analysis → AST
```

A DFA recognizes regular character patterns used by lexical analysis; it does not replace the recursive-descent parsers or recognize nested programming-language syntax. The lab provides these bounded educational automata:

- Identifier: `letter_or_underscore (letter_or_underscore | digit)*`
- Integer: `digit+`
- Arithmetic operator: exactly one of `+`, `-`, `*`, `/`, `%`
- Relational operator: `<`, `>`, `<=`, `>=`, `==`, `!=`
- Whitespace: one or more spaces or tabs

The graph shows the authoritative backend states and transitions. Run performs a complete simulation; Previous step and Next step move through the returned trace, while Reset clears it. Rejected inputs report the first failed transition or a non-accepting final state. Empty input is evaluated by the selected automaton rather than a global default.

The frontend exposes Code Analyzer and Automata Lab as top-level workspace tabs. Switching tabs preserves the analyzer source and language selection. Automata Lab includes a Source Token Explorer: it reuses the current Editor A analysis when available, or loads the source through `POST /api/analyze`, then lists real lexer tokens in source order with type and line/column location. Selecting a token uses only its matching educational DFA; unsupported categories remain visible with an explanation and are never routed through an unrelated automaton. Refreshing source or changing language clears stale token selections and traces.

The integrated flow is:

```text
Editor A source → existing lexer/analyzer → real token list → category mapping → matching DFA → character trace
```

Dedicated token mappings currently cover identifiers, digit-only integer literals, single-character arithmetic operators, and supported relational operators. The lexer does not emit ordinary whitespace tokens, and strings, characters, keywords, delimiters, layout tokens, unsupported operators, and other categories intentionally show `No dedicated DFA`. Syntax diagnostics remain separate from lexical diagnostics and DFA demonstration results.

Automata API endpoints:

- `GET /api/automata` lists available patterns.
- `GET /api/automata/{automaton_id}` returns states, accepting states, and transitions.
- `POST /api/automata/{automaton_id}/simulate` accepts `{ "input": "student2" }` and returns the execution trace.

Simulation input is limited to 2,000 characters. These automata are demonstrations of regular lexical patterns and are not claims of complete Python or C lexical compatibility.

When recovery is possible, malformed statements remain in the partial tree with `attributes.incomplete: true`. Missing or invalid expressions are represented as `ErrorExpression` nodes with an error code and message. These nodes are not valid executable or semantic results; the application never executes submitted code.

## Mini Python grammar

Grammar version: `mini-python-1.0`.

```text
program ::= statement*
statement ::= assignment | print_statement | call_statement | if_statement | while_statement | for_statement | function_definition | return_statement | import_statement | from_import_statement | try_statement | raise_statement | with_statement | pass | break | continue
assignment ::= IDENTIFIER "=" expression NEWLINE
print_statement ::= "print" "(" expression ")" NEWLINE
call_statement ::= IDENTIFIER "(" [expression ("," expression)*] ")" NEWLINE
if_statement ::= "if" expression ":" NEWLINE INDENT statement+ DEDENT ("elif" expression ":" NEWLINE INDENT statement+ DEDENT)* ("else" ":" NEWLINE INDENT statement+ DEDENT)?
while_statement ::= "while" expression ":" NEWLINE INDENT statement+ DEDENT
for_statement ::= "for" IDENTIFIER "in" expression ":" NEWLINE INDENT statement+ DEDENT
function_definition ::= "def" IDENTIFIER "(" [IDENTIFIER ("," IDENTIFIER)*] ")" ":" NEWLINE INDENT statement+ DEDENT
return_statement ::= "return" [expression] NEWLINE
import_statement ::= "import" module_name ["as" IDENTIFIER] ("," module_name ["as" IDENTIFIER])* NEWLINE
from_import_statement ::= "from" module_name "import" IDENTIFIER ("," IDENTIFIER)* NEWLINE
expression ::= comparison
comparison ::= additive (("==" | "!=" | "<" | ">" | "<=" | ">=") additive)*
additive ::= multiplicative (("+" | "-") multiplicative)*
multiplicative ::= unary (("*" | "/" | "%") unary)*
unary ::= ("+" | "-") unary | primary
primary ::= NUMBER | STRING | IDENTIFIER | call | "True" | "False" | "(" expression ")"
call ::= IDENTIFIER "(" [expression ("," expression)*] ")"
collection ::= list | tuple | dictionary | set
```

The beginner-level subset uses spaces for indentation; tabs produce a diagnostic. Blank lines and comment-only lines are ignored. Comments begin with `#` and continue to the end of the line. It supports assignments to names, indexes, and members; calls; `if`/`elif`/`else`; `while`/`for` with optional `else`; `range(...)` syntax; arithmetic, comparison, membership, identity, boolean, bitwise, shift, floor-division, and power operators; `None` and booleans; simple function definitions and returns; `import`/`from ... import ...`; collections; indexing/slicing; member access; `try`/`except`/`finally`; `raise`; `with`; and loop-control statements. This is syntax-only analysis: imports and calls are never executed, names are not resolved, and comprehensions, decorators, annotations, and advanced Python semantics remain outside the declared scope.

## Mini C grammar

Grammar version: `mini-c-1.0`. Mini C is an educational subset and is not an ISO C compiler.

```text
program ::= preprocessor_directive* declaration_or_statement*
declaration_or_statement ::= declaration | statement | function_definition
declaration ::= type_specifier IDENTIFIER ("[" expression "]")* ("=" expression)? ";"
type_specifier ::= "int" | "float" | "double" | "char" | "bool" | "void"
typedef_declaration ::= "typedef" type_specifier IDENTIFIER ";"
struct_declaration ::= "struct" IDENTIFIER "{" declaration* "}" ";"
enum_declaration ::= "enum" IDENTIFIER "{" IDENTIFIER ("," IDENTIFIER)* "}" ";"
statement ::= assignment | printf_statement | call_statement | block | if_statement | while_statement | for_statement | return_statement
assignment ::= IDENTIFIER "=" expression ";"
printf_statement ::= "printf" "(" STRING ("," expression)* ")" ";"
call_statement ::= IDENTIFIER "(" [expression ("," expression)*] ")" ";"
block ::= "{" declaration_or_statement* "}"
if_statement ::= "if" "(" expression ")" statement ("else" statement)?
while_statement ::= "while" "(" expression ")" statement
for_statement ::= "for" "(" (declaration | assignment) expression ";" expression ")" statement
function_definition ::= type_specifier IDENTIFIER "(" ["void" | parameter ("," parameter)*] ")" block
parameter ::= type_specifier IDENTIFIER
return_statement ::= "return" [expression] ";"
preprocessor_directive ::= "#include" ("<" module ">" | STRING)
expression ::= comparison
comparison ::= additive (("==" | "!=" | "<" | ">" | "<=" | ">=") additive)*
additive ::= multiplicative (("+" | "-") multiplicative)*
multiplicative ::= unary (("*" | "/" | "%") unary)*
unary ::= ("+" | "-" | "!") unary | primary
primary ::= NUMBER | STRING | CHARACTER | "true" | "false" | IDENTIFIER | "(" expression ")"
```

Mini C supports `//` and `/* ... */` comments, integer and decimal numbers, quoted strings, character literals, nested braces, declarations including `const`, multiple declarators, arrays and initializer lists, indexing, basic pointer/address-of syntax, named `struct`/`enum` variables, assignments including compound operators, calls, function prototypes and definitions, `struct`, `enum`, and `typedef` declaration syntax, logical/bitwise expressions, `if`/`else`, `while`, `do`/`while`, `for`, `switch`/`case`/`default`, `break`, `continue`, `return`, and syntax-only `#include` recognition. It does not execute functions, includes, or runtime behavior. Full pointer/type checking, struct member semantics, multidimensional semantics, and macro expansion remain outside the declared scope. Required semicolons are enforced. Empty input is invalid.

## Deployment

### Backend on Render

Create a Render Web Service from this GitHub repository, with root directory `backend`:

- Build command: `pip install -r requirements.txt`
- Start command: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
- Environment variable: `CODELENS_ALLOWED_ORIGINS=<deployed-frontend-origin>`

Render free services may sleep after inactivity. This is acceptable for the Phase 1 demonstration but may make the first request slow.

### Frontend on Vercel

Create a Vercel project from this GitHub repository, with root directory `frontend` and the Vite framework preset. Configure:

```text
VITE_API_BASE_URL=https://<verified-render-backend-host>
```

Redeploy after setting the variable. Then update the Render CORS value to the exact deployed Vercel origin and verify the browser network request.

Deployment is not considered complete until both public URLs and frontend-to-backend connectivity have been tested.

## Known limitations

- Mini Python and Mini C analysis are limited to their documented grammars.
- The native source textarea supports line-number navigation and selection, but does not provide full IDE-style syntax highlighting.
- Automata Lab uses simplified educational patterns and does not claim to be the exact internal transition implementation of the Mini Python or Mini C lexers.
- Mini Python and Mini C are planned subsets, not complete languages.
- No source code is executed.
- No database, saved history, or runtime execution exists yet. Phase 6 generation is Groq-only; the dual-editor milestone independently validates both source versions and compares their static analysis results.
- Public free-tier hosting may have cold starts and usage limits.
